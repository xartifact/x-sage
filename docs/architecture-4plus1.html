① 场景视图（+1）

三类参与者。v3 的关键约束是客户端不持有数据：AI 坐在客户机上，只发请求、收文本；服务端是唯一的真源与唯一的渲染者。浏览器访客走同一批端点。

③ 过程视图

运行时是「单进程、无缓存、每请求重建」。v3 多了两件事：客户端可以在另一台机器上（一次往返拿到成品文本），以及写入口需要令牌。没有后台任务、没有热更新、没有写入队列。

运行期事实

  • 无状态：进程内没有缓存，重启即等于「重新从磁盘读数」，因此不存在「服务里的图落后于磁盘」。
  • 写入即文件：提案、checkpoint、graph.json、MANIFEST 全落在挂卷的 KB 路径，跨部署保留。
  • 有压缩：所有响应按 Accept-Encoding gzip；activate 文本 6,029 B → 2,567 B。
  • 有上限与鉴权：请求体 ≤ 256 KB；写操作需 Bearer token（常量时间比较）；HOST 非回环且无 token 时拒绝启动。
  • 静态资源：缺失文件回退 index.html（200 + text/html），不是 404。路径穿越被 startsWith(webDist) 拦住，实测 /..%2f..%2fetc/passwd 只返回首页。

⑥ 关键决策

v3 的取舍可以概括为「把路由与渲染关进一个分发器，把客户端变成纯传输，把写入口锁在 token 后面」。

决策替代方案理由代价（实测）
路由与渲染都在 service，CLI 只做传输 CLI 自己读 KB、自己拼文本（v2 的做法） 客户机不需要 KB；文本只有一个实现点，远程与本地输出逐字节相同（15/15 命令实测） 客户端每次操作至少一次网络往返；离线不可用（离线请用 --kb）
Activation 去 Graph 化 把 semantic 图发给客户端让它自己算 REQUIRES 客户端无需图算法；载荷从 37,950 B 降到 12,628 B（text 仅 6,029 B） 闭包在后端算，客户端无法自定义推导规则
每请求重建图，不缓存 启动时建图 + 文件监听失效 「文件即真源」，缓存只会制造不一致；22 概念只要 2ms 每次激活 ≈66 次读取；概念数线性膨胀
删除 SPA 的静态数据文件 继续生成 public/graph-data.json 落盘副本必然过期，且与 CLI 各自解析一遍 首屏依赖 API：后端未启动时页面只剩错误提示
写操作暴露为 HTTP，但要求 Bearer token 写只走 CLI；或不加鉴权 客户端与运维都能写；token 是唯一凭据，常量时间比较 单一共享 token，无按人撤销；CORS 仍默认 *（读接口公开）
把构建身份放进 /api/health 只看 200 判健康 200 无法区分新容器与旧容器；部署必须能自证版本 版本三元组要穿过 workflow→ARG→ENV→process.env，任一处改名即静默降级为 dev（已用契约测试锁住）
KB 挂卷给容器 镜像内自带 KB（v2 的做法） 客户端写入的提案、checkpoint、重建产物跨部署保留 首次部署需初始化卷内容；多副本会并发写同一份文件（单副本假设）

前三条是 v3 修复的（保留记录以便回归时对照），其余仍开放，全部可复现。

#问题触发实测后果位置
1 合并提案不幂等 开放 按文件名合并一个已 approved 的提案 同一条边被重复追加：0 → 1 → 2，图里出现重复边且 validate 不报错（重复边被当作合法） service/write.ts merge 循环
2 写端点曾无鉴权 已修 任意网页对 POST /api/checkpoints/:id 发简单请求 修前：跨站请求返回 201 并落盘。修后：无 token 401，且 HOST 非回环时无 token 拒绝启动 server/app.ts · server/index.ts
3 CLI 与 API 边视图曾不一致 已修 edges decision --type depends-on vs 同名 API 修前：CLI 5 条、API 7 条（含 derived）。修后：同一分发器，derived 显式开关，两侧都是 5 条 / 7 条 service/api.ts
4 frontmatter 序列化不转义引号 开放 atom 含 " 时 merge atom: "He said "no": final" 重新解析变成 He said ，正文静默截断。v1 遗留，v2 通过 HTTP 暴露后更容易触发 core/manifest/parse.ts
5 MANIFEST 无 staleness 检查 开放 手改 MANIFEST.md 或忘记 manifest --write 追加一行垃圾后 validate --graph 仍报「graph.json is current / no issues」，AI 开卷读到的是过期索引 service/validate.ts 只检查 graph.json

7 激活载荷曾重复 9 次边数组 已修 GET /api/concepts/decision 修前 37,950 B（28,449 B 是同一份边复制到每个邻居）。修后 JSON 12,628 B，text 6,029 B service/query.ts 已去重

9 错误合同曾不统一 已修 未知 API 路由 / 非法 checkpoint 体 修前：未知路由纯文本 404；非法 PUT 体把序列化 ZodError 塞进 error。修后：统一 {error} 或按 format 的纯文本，checkpoint 体报首个字段错误 app.ts onError

12 checkpoint 不校验概念存在性 POST /api/checkpoints/does-not-exist 返回 201 并写入 does-not-exist-s1.json service/write.ts
13 docs 与实现脱节 已修 — 修前：测试数、已删字段、不存在的命令。修后：AGENTS.md / CLAUDE.md 与实现对齐 AGENTS.md:38,87,146
14 viz 无测试，且仍用 innerHTML molecule 含 HTML dangerouslySetInnerHTML + 自写 markdown 转换；@x-sage/core 依赖与 vite alias 已无任何 import DetailPanel.tsx · vite.config.ts
剩余优先级：① 合并幂等（会写坏数据且无回收路径）→ ② 用真正的 YAML 序列化替换手写 frontmatter（静默截断）→ ③ MANIFEST staleness 检查（AI 开卷读过期索引）→ ④ 对称性回到 RELATION_SPECS。前三条各是十行级改动，现有测试可直接保护。

不是缺陷，但要知道

  • graph.json 重复边不报错：把全图边复制一份后 validateGraph 仍返回 valid（无 dangling / cycle），所以「重复追加」这类 bug 没有兜底。
  • KB 已挂卷（./data/kb），因此写入会持久；代价是首次部署前要先放一份 KB 进去，否则卷为空。
  • KB 内 9 个文件仍未纳入 git（含全部 5 个 L3 概念与 2 个 checkpoint）。CI 的 validate 用的是工作区内容，因此本地全绿而干净 clone 只有 17 个概念。
  • 服务绑定：开发默认 127.0.0.1，容器里是 0.0.0.0，对外仅靠宿主机端口映射。TLS 仍缺——token 走明文 HTTP，公网部署前必须加反向代理。
  • 单一共享 token：无法按人撤销，也没有审计。轮换即所有人同时失效。
