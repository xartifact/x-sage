两套真源，一个开关：文件与 SQLite 并存期的存储架构 概念正文在 Markdown 与 knowledge.db 之间搬迁；权威由「数据库是否存在」决定。搬迁本身是稳的，边界不是。

本文回答：数据以什么形态落在哪、谁有权写、崩溃与并发时会发生什么。所有结论来自当前工作区代码 + 在 KB 副本上的实测。

结论

结构化侧的设计是对的。SQLite 权威把所有写入收敛成「提案 → 审阅 → 单事务应用」：基线由服务端判定（expectedRevisionFor），批准在 BEGIN IMMEDIATE 里复核并应用，关系写入后跑图校验，断言只有 accepted 才进权威。实测 12 次并发提案全部成功落库、无不一致；两边都改动时导入报 conflict 并保留权威记录。读路径也因此从每次全量解析降到 1.2 ms。
边界是坏的，而且坏得安静。三处：
1. 权威判定失败即降级。storeExists 捕获所有异常后返回 false，所以数据库损坏、权限错误、schema 不符都会让整个 KB 静默切回 旧 Markdown，读到的是一切迁移前的数据，写操作继续在文件上成功——没有任何告警。
2. 会话状态没有进入结构化模型。迁移后 POST /frontier 与 PUT /checkpoints/:id 仍然直接改文件（8 个旧写端点里只有这 3 个没加权威检查），而 knowledge.db 里根本没有对应表。
3. 备份文档与 WAL 冲突。库跑在 WAL 模式，提交先落在 -wal；文档给的 tar czf kb-backup.tgz kb/default 若在运行中执行、或只复制 knowledge.db，拿到的备份会缺行甚至「no such table」。

按收益/代价排序：权威判定不许 fail-open → frontier/checkpoint 纳入结构化模型（或明确拒绝写） → 备份改用 VACUUM INTO / .backup → schema 版本显式校验。前三件各是十行级改动，现有 336 个测试可直接保护。

① 双权威：一个开关决定谁是真相

开关在 packages/service/src/authority.ts：storeExists(root) 为真则 structured，否则 markdown。它不是配置项、不是请求参数、也不能按路由选择——每个请求进来都重新判一次。

② SQLite 布局：一个 KB 一个文件

路径由 registry 解析出的 KB 根决定（knowledgeDbFile），不接受客户端传入的 id，因此两个 KB 无法互相寻址。实测 22 个概念导入后：knowledge.db 204,800 B + -wal + -shm 32,768 B。

表角色关键约束
concepts概念记录：atom、layer、domain、body、revisionsource_hash / source_revision 用于把「文件变了」与「权威变了」分开
relations断言的关系，唯一一张表PRIMARY KEY (from_id, type, target)；概念行里没有 edges 副本
claims可审阅的断言（premise / constraint / …）status ∈ accepted / superseded / rejected，只有 accepted 进检索

连接与持久化设置

openStore 每次调用都新建连接、finally 关闭（readStructured 与 withStore）。这样回滚删库后不会有旧连接把文件吊住。实测生效的 pragma：

PRAGMA值含义

user_version 那一行是缺陷：把库标记成 99 后所有读仍然 200（实测）。没有 if (current > SCHEMA_VERSION) throw，未来版本的库会被当前代码当作自己的来解释。

③ structured 写入：一个事务，四道门

结构化侧的写入只有一条路：先存提案，再由审阅应用。没有「直接改」的端点。

场景结果

这层是这次改动里最扎实的部分。锁不再依赖 .write.lock 文件，而由 SQLite 的 BEGIN IMMEDIATE + busy_timeout 提供；跨文件的两步写（概念 + 提案状态）变成了同一个事务。

④ 分裂：迁移之后仍有写入落在文件上

8 个 markdown-era 写端点里，5 个加了 authorityOf(ctx) === "structured" 检查并返回 409。另外 3 个没有：POST /frontier、POST /checkpoints/:id、PUT /checkpoints/:id。而 knowledge.db 里没有 frontier 表，也没有 checkpoint 表。

元素 7 · 连线 3 · 交叉 0 · 穿框 0

结构化表清单（实测）：assets, claims, concepts, evidence, evidence_targets, meta, proposals, relations, vectors。没有 frontier、checkpoints。

后果不是「少一个功能」，而是权威被切成两半：概念与关系在数据库，会话进度与未解张力在文件。备份只做数据库会丢后者；只做文件会丢前者。而 AI.md 要求 AI 每次开场读 MANIFEST.md 与 frontier.md——前者现在由数据库投影，后者仍是文件。

保证markdown 权威structured 权威

结构化侧把「并发」与「跨文件原子」两项从红转绿，同时把「单文件可备份」从绿转红。这不是退步，是代价转移；问题在于新的代价没有被写进运维文档，而旧文档里的备份命令在新模式下是错的。

⑦ 修复顺序

顺序动作为什么排这里
1权威判定 fail-closed（A1）唯一会让人在不知情下读旧数据的缺陷；改动在 storeExists 一处
2frontier / checkpoint 明确归属（A2）两半权威现在都在长；加 409 是十行，建表是中等改动
3备份改 VACUUM INTO + 前置 checkpoint（A3）已有备份流程在当前模式下会静默产坏备份
4schema 版本校验 + synchronous 决定（A4, A5）防止未来库被旧代码误读；把持久化强度变成显式选择
5文件权威侧的锁与序列化（B1–B6）只在回滚路径生效；等 1–4 稳定后再动，避免两套写入同时改
不要动的部分：relations 单表、revision 基线的四种粒度、审阅即唯一写入路径、断言 accepted 才进检索、向量与断言分开返回、资产按 sha256 内容寻址。这些是本系统目前最值钱的设计，缺陷全在权威切换的边界与会话状态的归属上，不在数据模型本身。
