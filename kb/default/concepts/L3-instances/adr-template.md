# ADR 模板 Architecture Decision Record Template

## 核心内容（molecule）

ADR（架构决策记录）是将决策可追溯性具象化为可执行文档实践的具体实例。每个 ADR 记录一个架构决策及其语境、选项、推理过程。它不是设计文档（描述系统是什么），也不是需求文档（描述系统应做什么），而是决策文档（描述为什么系统是现在这样）。

### 完整 ADR 模板

```markdown
# ADR {编号}：{决策标题}

## 状态
{提议 / 已接受 / 已废弃 / 已替代}

## 决策者
{做出该决策的个人或团队}

## 日期
{决策日期，格式：YYYY-MM-DD}

## 语境
{决策时的背景信息，包括：
- 当前系统的状态和问题
- 需要解决的核心张力
- 已知的约束条件
- 相关的业务目标
- 哪些信息是确定的、哪些是不确定的}

## 目标
{决策试图达到的具体结果，而非解决方案}

## 选项

### 选项 A：{方案名称}
- **描述**：{简要说明方案的核心思路}
- **优点**：
  - {优点1}
  - {优点2}
- **缺点**：
  - {缺点1}
  - {缺点2}
- **成本估算**：{开发/迁移/维护成本}

### 选项 B：{方案名称}
- **描述**：{简要说明方案的核心思路}
- **优点**：
  - {优点1}
  - {优点2}
- **缺点**：
  - {缺点1}
  - {缺点2}
- **成本估算**：{开发/迁移/维护成本}

## 决策结果

**选择**：选项 A

**理由**：
{逐条说明为什么选A不选B。每个理由对应语境中的一个约束或目标。}

**不确定性**：
{决策时已知的不确定因素——哪些信息当时不可获取？哪些假设可能失效？}

## 影响

**正面**：
{选择A带来的预期正面影响}

**负面**：
{选择A带来的预期负面影响——不是缺点，而是已知的trade-off}

## 替代方案回顾

{将来的语境变化可能使哪些被放弃的方案重新变得可行？
记录语境变化的触发条件，如：用户量达到X时，选项B可能成为更好选择}

## 备注
{额外的上下文、参考链接、后续决策的联系}
```

### 完整示例：选择 Monorepo 而非 Polyrepo

```markdown
# ADR 001：项目采用 Monorepo 架构

## 状态
已接受

## 决策者
前端架构组（张三、李四、王五）

## 日期
2025-03-15

## 语境
我们正在启动一个新平台项目，包含三个前端应用（用户端、管理端、组件库）、两个后端服务（API网关、业务服务），以及共享的类型定义和工具库。团队共12人，分3个小组。项目预计维护周期3年以上。

当前已知：
- 所有服务使用 TypeScript
- 代码共享需求高（类型定义、模式库必然跨项目共享）
- 团队在同一个办公室，沟通成本低
- CI/CD 基础设施尚在搭建中
- 历史教训：之前项目因跨仓库版本不同步导致过生产事故

不确定因素：
- 项目规模未来是否扩大到20+人的团队
- 是否会有外部团队加入
- 代码库体积增长速度

## 目标
- 最小化跨服务/跨应用的版本同步成本
- 支持长期维护（3年+）
- 降低新成员的上手成本

## 选项

### 选项 A：Monorepo（单仓库）
- **描述**：所有服务和应用放在同一个 Git 仓库中，使用模块化管理
- **优点**：
  - 原子提交：跨服务的变更可以在一个 PR 中完成
  - 共享代码零版本管理成本：类型定义直接引用
  - 统一的构建、测试、部署流程
  - 新成员只需克隆一个仓库即可开始工作
- **缺点**：
  - 代码库体积增长快，可能影响 git 操作性能
  - 理论上存在权限控制问题（但当前团队不需要跨服务权限隔离）
  - 构建系统需要支持增量构建
- **成本估算**：初期搭建结构化目录和构建脚本约2周，无持续维护额外成本

### 选项 B：Polyrepo（多仓库）
- **描述**：每个服务/应用独立仓库，共享代码通过 npm 包管理
- **优点**：
  - 仓库独立，团队可独立迭代
  - 代码库体积可控
  - 权限精细控制
- **缺点**：
  - 跨仓库变更需要多个 PR，同步成本高
  - 共享代码需要版本发布流程，修复一个 bug 需要经过 npm publish → 依赖升级
  - 历史教训表明版本不同步已导致过线上事故
  - 新成员需要克隆多个仓库并理解仓库间依赖关系
- **成本估算**：初期搭建快（1周），但持续的版本管理成本高（预估每跨服务变更额外1-2天同步时间）

## 决策结果

**选择**：选项 A（Monorepo）

**理由**：
1. 代码共享是硬需求（类型定义、模式库必然共享），Monorepo 的零版本管理成本直接回应了这一核心约束。
2. 12人团队、同一办公室的团队结构使得 Monorepo 的协调优势可以充分发挥。
3. 历史教训（版本不同步导致生产事故）是高风险规避信号——Monorepo 消除了这类风险。
4. 当前团队不需要跨服务权限隔离，Polyrepo 的优势在此语境下不存在。

**不确定性**：
- 未来代码库体积增长速度未知——需监控并计划在 git 性能下降时引入 sparse checkout
- 若未来有外部团队独立维护某个服务，可能需拆出子仓库

## 影响

**正面**：
- 跨服务类型变更可以在一个 PR 中完成，开发效率提升
- CI/CD 流程统一，降低运维复杂度

**负面**：
- 构建系统需配置增量构建，初期搭建投入2周
- 若后续需要拆分，数据迁移成本较高

## 替代方案回顾

- 当团队规模超过20人或出现外部贡献者时，选项 B（Polyrepo）配合自动化版本管理工具（如 Changesets）可能重新变得可行
- 触发器信号：团队人数 > 20 || 有外部团队加入 || 单个 CI 运行时间 > 30分钟

## 备注
- 本决策与 ADR 003（构建工具选择）直接关联
- 参考：Google、Meta、Uber 的 Monorepo 实践
```

### 维护建议

- 每个 ADR 以文件形式存储在代码仓库的 `docs/adr/` 目录下，与代码同版本控制
- 编号连续不重用，即使 ADR 被废弃也保留
- 状态为"已替代"的 ADR 需要标记"替代者"字段，指向新的 ADR 编号
- 建议在每个 Sprint Review 中回顾最近 ADR 的状态——语境变化后，某些决策可能需要重新评估

## 张力与开放问题

- **文档负担**：ADR 的文化阻力通常不是"不知道怎么写"，而是"没时间写"。如何让 ADR 写作成为开发流程的自然环节而非额外负担？
- **决策颗粒度**：什么级别的决策需要 ADR？每个技术选择都记录会淹没在文档中，完全不记则失去追溯能力。颗粒度的判断标准是什么？
- **ADR 的保质期**：语境变化后，ADR 可能不再适用。如何处理"不再适用但未正式废弃"的 ADR？是否需要引入定期的 ADR 审计机制？
