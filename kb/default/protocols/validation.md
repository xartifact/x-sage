# 验证模式协议

## 适用场景

- 用户对某个论断提出质疑（"真的是这样吗？"）
- 需要检验概念之间的逻辑一致性
- 评估某个决策或方案的弱点
- 寻找盲点、隐性假设和未被考虑的对立面

## 核心策略

**优先加载 `contradicts` 边节点，然后沿 `depends-on` 回溯前提。**

验证不是建设——它是拆解。不从 enaables 展开（那是探索的事），而是从矛盾入手，检查系统的脆弱点。

## 执行流程

### 第一步：定位检验目标

1. 识别用户要验证的概念或论断
2. 在 MANIFEST 中查找对应概念
3. 列出该概念的所有 `contradicts` 边

```
[验证] 检验目标：{概念ID}
[验证] 发现矛盾边：{列出所有 contradicts 边}
[验证] 发现对立概念：{对立概念列表}
```

### 第二步：加载矛盾子图

1. 加载检验目标的完整 molecule
2. 加载所有 `contradicts` 边指向的对立概念的完整 molecule
3. 如果对立概念自身有 `contradicts` 边，递归加载（最多 2 层）

```
[验证] 已加载矛盾子图：{概念列表}
```

### 第三步：回溯前提链

1. 从检验目标出发，沿 `depends-on` 边回溯
2. 加载所有直接依赖的 L0/L1 前提概念
3. 检查前提是否真的支持当前论断——前提中的条件是否被满足？

```
[验证] 前提链：{概念A} → depends-on → {概念B} → depends-on → {概念C}
[验证] 前提条件检查：{哪些前提条件在当前语境下成立/不成立}
```

### 第四步：辩证分析

对每一对矛盾，执行以下分析：

1. **矛盾性质**：逻辑矛盾（A ↔ ¬A）还是语境矛盾（A在语境X下 ↔ B在语境Y下）？
2. **成立条件**：矛盾双方各自在什么语境下成立？
3. **消解可能**：是否可以通过引入新概念或重新划界来消解矛盾？
4. **置信度评估**：双方的 confidence 是否反映了实际的确定性差距？

```
[验证] 辩证分析：{概念A} vs {概念B}
  - 矛盾性质：{逻辑矛盾 / 语境矛盾}
  - A 成立语境：{...}
  - B 成立语境：{...}
  - 消解可能：{可消解 / 不可消解 / 待定}
  - 置信度差距：{A=confirmed, B=hypothetical → A 优先}
```

### 第五步：边界测试

验证一个概念是否在其声称的范围内成立：

1. 找到概念中隐含的 **语境限定**（哪些语境下成立）
2. 构造一个 **边界案例**：刚好在成立范围边缘的语境
3. 判断概念在边界案例下是否仍然成立

```
[验证] 边界测试：{概念ID}
  - 声明成立范围：{...}
  - 边界案例：{...}
  - 边界上是否成立：{是 / 否 / 部分成立}
```

### 第六步：写回结果

1. 如果发现新的矛盾 → `flag-tension` 写入 `frontier.md`
2. 如果发现 atom 描述不足以区分相似概念 → `refine-atom` 写入 `proposals/atoms/`
3. 如果发现概念的 confidence 需要调整 → `propose-edge` 写入 `proposals/edges/`（更新 confidence）

## 输出格式

```
## 验证报告：{检验目标}

### 矛盾分析
{每一对矛盾的辩证分析}

### 前提回溯
{依赖链 + 前提条件检查结果}

### 边界测试
{边界案例 + 成立性判断}

### 置信度修正建议
{如有需要调整的 confidence，列出建议}

### 未验证节点
{回溯中发现但未深入检验的前提概念}
```

## 注意事项

- 验证模式 **必须主动寻找反面**——不要只确认用户的假设，要主动提出质疑
- `contradicts` 边是最高优先级，即使只有一条也要加载
- 逻辑矛盾和语境矛盾的处理方式完全不同——前者需要修正概念，后者需要补充语境条件
- 不要把 `hypothetical` 的矛盾当成 `confirmed` 的矛盾来处理——置信度影响推理权重
- 如果检验目标没有 `contradicts` 边，这本身就是一个信号：可能存在未记录的矛盾，值得写入 frontier
